# B位置差异的算子级首轮核对

## 范围与方法

仅使用224和256卡iter60 trace，不读取32卡、不调整预测。固定抽样224的PP5/6（此前40/60/80重复下降边）和256的PP1/14（早晚位置对照，不预设单调下降）。每stage仅lane0代表rank；覆盖224的B0–2及256的B0–3，共4份trace、14个B。

沿用唯一runtime correlation与CPU backward_step包络归属规则，按同名kernel记录数量、累计时长及并集，并拆分B包络为“归属设备事件并集＋未覆盖间隔”。14个B边界与冻结曲线一致，分解闭合验证通过。原trace SHA校验通过。

未覆盖间隔仅表示没有已归属本B的设备事件，不能直接称为GPU空闲、CPU延迟或通信等待。kernel累计时长可能重叠，不能作为壁钟贡献相加。尚未完成重计算/真反向和每层算子的细分归属。

224中三个B的ace_notify_dispatch均为4次，但累计时长分别减少7.380、53.414、23.586ms；SendRecv均为36次，累计时长减少13.159、6.613、10.070ms。说明下降伴随同步/通信相关kernel耗时变化，并非仅计算算子变快。notify不是纯数据传输成本，SendRecv尚未逐事件确认CP/PP身份。拷贝、Add和不同GEMM实现也有差异，不能忽略。

256端点对照中，B1/2/3包络更短，但归属设备活动并集略增；B0包络略增。说明这一抽样不支持“计算量或所有算子普遍变小”的解释，块内事件间隔及重叠组织值得优先核对。不同GEMM实现的调用数量有变化，仅凭名字不能推断token、形状或计算量原因。

## 当前可用表述

“B的位置差异包含同步/通信相关算子驻留时间变化，以及归属设备活动之间的间隔变化；不是已证明的纯计算误差或纯带宽误差。”

这是目标trace内部的算子行为线索，不能单凭这4份trace解释32→256的全部6.16%误差，也不能声称224/256具有相同机制。已有中间B oracle解释87.9%的结论仍是块级定位，与本轮算子诊断分开。
