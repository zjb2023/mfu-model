# Combine同步间隔跨stage核对与1F1B条件诊断

## 范围与事实

256卡iter60，PP1–PP14每stage lane0代表rank，全部4个B，共14份原trace、56个B。原trace SHA全部核验；B GPU包络与已封存1F1B诊断数据匹配。仅目标256数据，不读取32源，不修改正式模型。

每B选定重计算FusedCombine及反向FusedDispatchBackward共8个框架调用。统计其Synchronize API与同device所有stream均无记录设备活动区间的交集，作为“Combine同步间隔”指标。不能将该指标等同纯CPU开销、纯通信或可消除等待。

## 是否是跨stage波动主要来源

| B | Combine间隔与B包络的Pearson相关 | Combine间隔范围ms | 相邻stage间隔下降边数 |
|---|---:|---:|---:|
| B0 | 0.641 | 16.266–51.026 | 9/13 |
| B1 | 0.723 | 16.741–59.856 | 8/13 |
| B2 | 0.743 | 16.546–77.931 | 8/13 |
| B3 | 0.444 | 18.595–55.299 | 8/13 |

这是有相关性的因素，但非单调stage规律，也未证明是跨stage波动的唯一或主要物理来源。此前93.6%仅是PP1/PP14 B1两点“无记录设备间隔差”的覆盖，不能扩展为全部B或整个1F1B归因。

## 条件DAG诊断

参考量固定为目标256 PP1、同microbatch的Combine同步间隔S(1,m)。所有F、PP通信、首尾B与依赖保持冻结值。

诊断一：冻结中间B成本C改为`C + S(stage,m) - S(1,m)`。这只注入目标内部的空间差异；不是32→256成本差，也未证明同步间隔可独立线性加到B成本。重新调度，而不是累加各B差值。

| 情景 | 1F1B ms |
|---|---:|
| 冻结预测 | 21653.358 |
| 仅注入Combine间隔相对PP1的位置差异 | 21516.801 |
| 用目标实测替换全部中间B（既有oracle） | 20548.686 |
| 目标实测1F1B | 20396.013 |

条件缩短136.557ms，占原1257.345ms高估的10.86%，占中间B替换带来1104.672ms改善的12.36%。这一诊断不足以解释“大部分约1秒偏差”，更不能将目标数据替换结果作为独立预测。

诊断二：在中间B已换目标实测的背景中，把各stage间隔统一成目标PP1，即`B实测 - S(stage,m) + S(1,m)`。1F1B从20548.686增至20707.803ms，增加159.117ms。这是另一背景下的条件空间敏感性（约占中间B原诊断改善的14.4%），并非置信区间或第二个独立归因项，不能与136.557相加。

## 结论与下一步

可以说Combine同步间隔是跨stage B变化的重要线索，但目前条件诊断只有约0.14–0.16秒的整段影响量级，不能解释约1.1秒中的大部分。目标stage间位置差异与32源成本对目标整体偏高是两类问题；只看目标数据无法判定后者的物理组成。

下一步先保留本诊断，不拟合PP效率。若继续追踪剩余约0.95秒的量级，需另行比较源32的同口径模块成本与目标256的对应模块（计算、CP、EP、同步/间隔），再做单项DAG诊断；在“只分析224/256”的限制内只能继续研究目标内部差异，不能承诺解释完整外推偏差。
